Sandbox

A sandbox is a container you start on your own machine, holding your own agent, the Motir CLI and your checkouts — and nothing else. You bring your own agent credential, mounted read-only; the loop runs inside, so a misbehaving agent reaches your work tree and not the rest of your machine.

Before you start

  • Docker, running. Built for linux/amd64 and linux/arm64, so Apple Silicon is native. There is no build step — you pull.
  • Your agent’s own sign-in, on this machine. Its credential mount is read-only, so the container can use a sign-in and can never perform one.
  • Your workspace root — the folder that CONTAINS your checkouts. A project usually spans several repositories and the loop runs across all of them.

Which agent do you use?

also supported or

Every command below is for Claude Code. Switching rewrites the tag and the credential mount in steps 1, 2 and 2b — the three places they appear.

Set it up

Five steps. Each one is a single thing to do.

  1. Pull the image for your agent Command

    There is no build step — the image is published per agent profile. Swap the tag for the agent you use.

    pull 

    docker pull ghcr.io/moooon-b-v/motir-sandbox:claude

  2. Start the container from your workspace root Command

    Run it from the folder that contains your checkouts, not from any one of them.

    run 

    docker run -it --rm --pull=always \
  -v "$PWD:/workspace" \
  -v motir-auth:/home/node/.config/motir \
  -v "$HOME/.claude:/home/node/.claude:ro" \
  ghcr.io/moooon-b-v/motir-sandbox:claude

    Using VS Code instead? Steps 2a–2c below replace this one. Everything after is the same either way.

  3. Sign in, inside the container Command

    A code and a URL are printed; approve it in any browser. The sign-in lands on the motir-auth volume, so you do this once.

    in the container 

    motir login

  4. Link the folder to your project Command

    Swap ACME for your project key. If your workspace has exactly one project, drop the flag — that is the whole step.

    in the container 

    motir link --project ACME

  5. Check it — all green is the end of this page Command

    Auth, link, the agent binary and its credential. This is the only thing that tells you the container actually got what you passed it.

    in the container 

    motir doctor

Or start it from VS Code instead

The same confined image, as a dev container. These three replace step 2 — steps 3 to 5 are the same either way.

  1. Install the Dev Containers extension In your editor

    Extensions view, or the command palette — ⇧⌘P on macOS, Ctrl+Shift+P elsewhere, F1 on all three — then Extensions: Install Extensions. Two of these three steps happen in the palette, so it is worth pinning now.

  2. Create the dev container config Command

    Run this in the folder you are mounting. One paste: it makes the .devcontainer folder and writes the file into it. Do not try to create them from a file picker — Finder and most GUI pickers refuse a name beginning with a dot, and refuse it without saying why.

    your machine — in the folder you are mounting 

    mkdir -p .devcontainer
cat > .devcontainer/devcontainer.json <<'JSON'
{
  "name": "Motir sandbox (Claude Code)",
  "image": "ghcr.io/moooon-b-v/motir-sandbox:claude",
  "workspaceFolder": "/workspace",
  "workspaceMount": "source=${localWorkspaceFolder},target=/workspace,type=bind",
  "mounts": [
    "source=${localEnv:HOME}/.claude,target=/home/node/.claude,type=bind,readonly"
  ],
  "remoteUser": "node",
  "overrideCommand": true,
  "postStartCommand": "motir-sandbox-agent-config || true"
}
JSON

  3. Open the folder in the container In your editor

    Command palette → Dev Containers: Open Folder in Container…, and pick the folder you just wrote the file into. Its terminal is the same shell step 2 would have dropped you into — carry on at step 3.

Why it looks like this

The file that command writes

Reference, not a step — step 2b already wrote it. It is here for the reader who would rather create the file by hand, and because the quotes around <<'JSON' are load-bearing: they stop your shell expanding ${localWorkspaceFolder} and ${localEnv:HOME} before they reach the file. Those are Dev Containers substitutions and the editor resolves them.

.devcontainer/devcontainer.json

  "image": "ghcr.io/moooon-b-v/motir-sandbox:claude",
  "workspaceFolder": "/workspace",
  "workspaceMount": "source=${localWorkspaceFolder},target=/workspace,type=bind",
  "mounts": [
    "source=${localEnv:HOME}/.claude,target=/home/node/.claude,type=bind,readonly"
  ],
  "remoteUser": "node",
  "overrideCommand": true,
  "postStartCommand": "motir-sandbox-agent-config || true"
}

What the profile picker changes

Picking an agent above rewrites three things and nothing else: the image tag, the credential -v line, and the dev container's image, name and mounts. It is a control rather than a paragraph telling you to swap them yourself, because every command on this page has a Copy button and a reader who copies is a reader who did not read the swap instruction.

Nothing is kept that could go stale

--pull=always fetches the current image on every start and --rm keeps nothing behind, so there is no coming-back-to-it path that leaves you on a months-old CLI. Your sign-in survives it: it lives on the motir-auth volume, outside the container.

What it confines — and what it does not

Filesystem, confined. Network, OPEN by design — every agent needs its provider API. Privileges, unprivileged. Worth reading before you rely on it, because one of those three is an exception rather than a guarantee.

FAILED does not time out, and that is the design. Copied holds 1600 ms and reverts to Idle. Failed persists until the next successful copy or until focus leaves the pane, because a notice that has gone by the time the reader looks up is precisely the failure this state exists to prevent: they believe they hold the command and paste whatever was in the clipboard before.
The wording is the design's, not the builder's. Idle Copy · copied Copied · failed Copy failed, with the note reading Couldn’t reach the clipboard — select the text and copy it by hand. The accessible name is Copy the <caption> command, so two buttons on one page never announce identically.
Tokens, named. Button: border --el-border, ink --el-text-secondary on --el-page-bg, --radius-control. Copied: --el-tint-mint with --el-text-strong. Failed: --el-tint-peach with --el-text-strong — the same AA recipe every tinted surface in this tree uses. Focus ring: --el-accent, 2px, 2px offset. No hue is invented, and the state is never carried by colour alone: the LABEL changes in all three.

The PROFILE SELECTOR — and why it is not a step

Eight agents, plus the agent-less image. Picking one rewrites the tag and the mount in steps 1, 2 and 2b.

Which agent do you use?

also supported or

The page had ONE agent drawn in it, and that was a defect. The shipped page answers this with a paragraph AFTER the command — "swap both the tag and the -v line together" — and the first draft of this asset moved that paragraph BELOW the whole sequence, which made it worse. A copy button and a swap-it-yourself instruction cannot coexist: the affordance exists so a reader can work down the page without reading, so seven readers in eight would have pasted a command for an agent they do not use, from a button that looked authoritative. The control is the fix, and it is the only fix that survives the copy button.
It is a CONTROL, not a step. Both step kinds are things the reader does OFF this page — in a terminal or in an editor — so admitting a third kind that happens ON it would break the rule the sequence rests on (every step is one action, and is either a command or a UI instruction). It sits directly above Set it up because steps 1, 2 and 2b cannot be written until it is answered — the same reasoning that made the profile matrix step 1 in the superseded motir-core asset, reaching a control instead of a table because this page now has a Copy button and that one did not.
States: unselected (--el-page-bg, border --el-border, ink --el-text-secondary) · hover (--el-muted) · selected (--el-accent ground with --el-accent-text, 600) · focus-visible (the same 2px --el-accent ring the copy button uses). role="radiogroup" with aria-checked, so a screen reader announces one selected of nine rather than nine buttons.
EIGHT profiles — and base is not a ninth. It is the agent-less IMAGE TAG, which is why it sits after an or rather than inside the tier grouping: no tier, no credential, no mount, and a reader choosing it is choosing to have no agent rather than choosing which one. (motir-core#2746 corrects cards that said "nine profiles including base"; AGENT_PROFILES has eight.) The superseded motir-core asset kept it out of its profile TABLE for the same reason — a row with nothing in three of its four columns. A PICKER is the one surface where it belongs, because choosing it is a real choice.
The tier break is a LABEL, not a second control. Both groups are published and both are built and smoke-tested; the split says how closely we track the vendor, never whether the profile works. Drawn as the word also supported between the two runs of chips rather than as a heading, a column or a tint — a reader choosing an agent is not choosing a tier.

Step 2 across the FOUR shapes — one mount, two, none, and a file

The variance a single drawn command hides. Every literal here is transcribed, not derived.

Claude Code · Codex · Kimi · Cursor · Goose · ONE credential mount — the ordinary shape

  1. Start the container from your workspace root Command

    run 

    docker run -it --rm --pull=always \
  -v "$PWD:/workspace" \
  -v motir-auth:/home/node/.config/motir \
  -v "$HOME/.claude:/home/node/.claude:ro" \
  ghcr.io/moooon-b-v/motir-sandbox:claude

OpenCode · TWO mounts — a config dir AND a data dir

  1. Start the container from your workspace root Command

    run 

    docker run -it --rm --pull=always \
  -v "$PWD:/workspace" \
  -v motir-auth:/home/node/.config/motir \
  -v "$HOME/.config/opencode:/home/node/.config/opencode:ro" \
  -v "$HOME/.local/share/opencode:/home/node/.local/share/opencode:ro" \
  ghcr.io/moooon-b-v/motir-sandbox:opencode

    OpenCode keeps configuration and credentials in two places, so it takes two -v lines. A design that assumes one silently drops the second.

Antigravity CLI · NO mount at all — and the precondition changes with it

  1. Start the container from your workspace root Command

    run 

    docker run -it --rm --pull=always \
  -v "$PWD:/workspace" \
  -v motir-auth:/home/node/.config/motir \
  ghcr.io/moooon-b-v/motir-sandbox:antigravity

    Antigravity keeps its token in the OS keyring, which has no portable file to bind — so there is no -v line for it, and you sign in inside the container rather than before you start. This is the one profile for which Before you start's second precondition does not apply.

Aider · a FILE, not a directory — plus a key from the environment

  1. Start the container from your workspace root Command

    run 

    docker run -it --rm --pull=always \
  -v "$PWD:/workspace" \
  -v motir-auth:/home/node/.config/motir \
  -v "$HOME/.aider.conf.yml:/home/node/.aider.conf.yml:ro" \
  -e ANTHROPIC_API_KEY \
  ghcr.io/moooon-b-v/motir-sandbox:aider

    Aider's credential is a model API key it reads from the environment, so this profile is the only one that adds a -e line. The bind is ~/.aider.conf.yml — a file, which must exist (even empty) or docker creates a directory in its place.

THREE of the eight profiles break the one--v-line shape, which is why this panel exists and why the selector cannot be a simple string substitution. OpenCode takes two mounts; Antigravity takes none and moves the sign-in inside the container; Aider binds a FILE and adds an -e. A build that treats the mount as one templated line is correct for five profiles and wrong for three.
Where the values come from — and the field to read. The build card TRANSCRIBES the per-profile table from motir-core packages/cli/src/agentProfiles.ts, the same transcribe-rather-than-import rule the page already follows for every other claim. Read sandboxMounts, never credentialPaths — that file's own docstring says so in terms: the two answer different questions and diverge on most of the eight profiles. Take the count from the docstring, not from here: it is four today, and MOTIR-4957's OPEN pull request (motir-core#2746) widens it to seven by re-pointing three profiles' probes at credential FILES while leaving sandboxMounts untouched. That pull request is evidence FOR this instruction rather than against it — the gap it opens makes deriving the mount from the probe list worse, not better. This asset draws the SHAPES; sandboxMounts is the source for the strings, and it is the field #2746 does not change.
