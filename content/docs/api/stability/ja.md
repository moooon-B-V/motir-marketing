公開読み取り API にはバージョンがあります。契約のバージョンは、配信される OpenAPI ドキュメントの `info.version` フィールドに含まれ、クライアントを壊す変更は、黙って編集されるのではなく、バージョンの更新として行われます。

## `v1` が保証すること {#the-guarantee}

`v1` が存在する間は、そのパスは移動せず、エラーの `code` の意味は変わらず、既存の条件に対するステータスは変わらず、フィールドの型や空値の許容も変わりません。これらを壊す可能性のある変更は `v2` になり、`v1` のリリースにはなりません。

### `v1` の中で、通知なしに許されること {#allowed-inside-v1}

- 新しいエンドポイント。
- 新しい任意のクエリパラメーター。
- レスポンスのオブジェクトに新しいフィールドを追加すること。
- 新しいレスポンスヘッダー。
- 開放的なものとして文書化されたフィールドへの新しい値。
- レート制限の上限の引き上げ。

### 新しいメジャーバージョンが必要なこと {#needs-a-new-major}

- フィールドの削除。
- フィールドの名前の変更。
- フィールドの型や空値の許容の変更。
- エラーの `code` の削除や、別の用途への転用。
- 既存の条件に対する既存のステータスの変更。
- 制限の厳格化。
- 任意のパラメーターを必須にすること。

## 利用者側の責任 {#your-obligation}

**クライアントは、未知のフィールドと未知の値を許容しなければならず、人間向けの `error` の文を解析してはなりません。** これは約束のもう半分であり、これがなければ上記の保証は成り立ちません。認識できないフィールドを拒否するクライアントは、このページが安全だとしている変更で壊れ、`error` を解析するクライアントは、言い回しが変わっただけで壊れます。`code` で分岐し、知らないものは無視すれば、追加的な変更はすべて、あなたにとって負担になりません。

## 非推奨化 {#deprecation}

非推奨の操作やフィールドには、**仕様の中で** `deprecated: true` が付けられ、その説明に理由と代替手段が記載されます。仕様を告知の手段としているのは、すべてのクライアントがすでに読んでいる唯一の成果物だからです。そのため、誰かがブログ記事を目にしていなくても、コードジェネレーターが非推奨を表面化させます。

古い動作は、告知された期間中は引き続き動作します。フィールドが不意に削除されることはありません。

## `v2` の登場のしかた {#how-v2-arrives}

`v1` と並んで、2 つ目のパスに配信される 2 つ目のドキュメントとして登場します。既存のものを書き換えるのではありません。`v1` は、`v2` が登場した日に動かなくなることはなく、`v1` を非推奨にすること自体も、同じ期間のルールに従った告知になります。

仕様の `info.version` は、アプリのリリース番号ではなく、API の契約のバージョンです。メジャーはパスのバージョンで、マイナーは上のリストにある追加的な変更で増え、パッチはドキュメントのみの修正で増えます。任意のレスポンスから `X-Motir-Api-Version` として読み取れます。どこで確認できるかは、[はじめに](/docs/api/getting-started)に記載されています。
