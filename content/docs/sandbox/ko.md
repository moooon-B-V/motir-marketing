샌드박스는 사용자의 컴퓨터에서 시작하는 컨테이너이며, 사용자 본인의 에이전트, Motir CLI, 체크아웃된 저장소만 들어 있고 그 밖의 것은 없습니다. 에이전트 자격 증명은 사용자가 직접 가져와 읽기 전용으로 마운트하며, 반복 작업은 컨테이너 안에서 실행됩니다. 따라서 잘못 동작하는 에이전트도 작업 트리에만 영향을 줄 수 있고 컴퓨터의 나머지 부분에는 닿지 않습니다.

## 시작하기 전에 {#before-you-start}

- **Docker가 실행 중이어야 합니다.** `linux/amd64`**와** `linux/arm64`용으로 빌드되어 있으므로 Apple Silicon도 기본 지원 환경이며 에뮬레이션은 없습니다. 빌드 단계는 없고 이미지를 받기만 하면 됩니다.
- **이 컴퓨터에서의 에이전트 자체 로그인.** 자격 증명 마운트는 읽기 전용이므로 컨테이너는 로그인 정보를 사용할 수는 있어도 갱신할 수는 없습니다. macOS의 Claude Code는 만나게 될 예외입니다. 토큰을 로그인 키체인에 보관하므로 마운트할 파일이 없으며, 대신 컨테이너 **안에서** `claude`에 로그인합니다. 이미지가 쓰기 가능한 설정 디렉터리를 제공하고 로그인이 그곳에 저장됩니다. (Antigravity도 같으며, 2단계에서 선택할 때 안내합니다.)
- **워크스페이스 루트, 즉 체크아웃된 저장소들을 포함하는 폴더.** 프로젝트는 보통 여러 저장소에 걸쳐 있고 반복 작업은 그 모두에 걸쳐 실행됩니다.

{{part:note-opencode}}

OpenCode는 설정과 자격 증명을 두 곳에 보관하므로 `-v` 줄이 두 개 필요합니다. 둘 다 필요합니다.

{{part:note-antigravity}}

Antigravity는 토큰을 OS 키링에 보관하는데, 키링에는 바인드할 이식 가능한 파일이 없습니다. 그래서 `-v` 줄이 없고, 시작하기 전이 아니라 컨테이너 안에서 로그인합니다. 위의 두 번째 사전 조건이 적용되지 않는 유일한 프로필입니다.

{{part:note-aider}}

Aider의 자격 증명은 환경에서 읽는 모델 API 키이므로, `-e` 줄을 추가하는 유일한 프로필입니다. 바인드 대상은 파일이며, 비어 있더라도 반드시 존재해야 합니다. 없으면 docker가 그 자리에 디렉터리를 만듭니다.

{{part:note-base}}

기본 이미지에는 Motir CLI만 있고 에이전트는 전혀 없습니다. 마운트할 것도 없고, Motir 자체 외에는 로그인할 것도 없습니다.

## 이렇게 생긴 이유 {#why}

### 프로필 선택기가 바꾸는 것 {#profile-picker}

에이전트를 선택하면 세 가지만 다시 작성됩니다. 이미지 **태그**, 자격 증명 `-v` 줄, 그리고 Dev Container의 `image`, `name`, `mounts`입니다. 바꾸라는 문장을 적어 두는 대신 컨트롤로 만든 이유는, 여기 있는 모든 명령에 복사 버튼이 있고, 복사하는 독자는 교체하라는 안내를 읽지 않은 독자이기 때문입니다.

모든 프로필에 자격 증명 디렉터리가 하나뿐인 것은 아닙니다. `opencode`는 두 개를 보관하므로 `-v` 줄이 두 개 필요합니다. `antigravity`는 토큰을 OS 키링에 보관하므로 줄이 없고 대신 컨테이너 안에서 로그인합니다. `aider`는 파일을 바인드하고 환경에서 모델 키를 읽습니다. 해당 프로필을 선택하면 단계에서 이를 안내합니다.

### 실행 명령에는 낡을 수 있는 것이 남지 않습니다 {#run-command}

`--pull=always`는 시작할 때마다 현재 이미지를 가져오므로, 프로필 태그가 이동해도 사용자가 알아차리지 않아도 그 이미지가 반영되고, `--rm`은 낡을 수 있는 것이 남지 않게 합니다. 돌아와서 다시 쓰는 별도의 경로는 없습니다. 바로 그것이 사람들이 읽고 있는 페이지보다 몇 달 오래된 `motir`를 쓰게 만들던 원인이었습니다. 로그인은 이 모든 것을 거쳐도 유지됩니다. 컨테이너 밖에 있는 `{{value:authVolume}}` 볼륨에 기록되므로 한 번만 로그인하면 이후 모든 실행이 이를 사용하며, 완전히 로그아웃하려면 `{{value:signOutCommand}}` 명령을 사용하세요. 오프라인으로 작업하시나요? `--pull=always`를 빼세요. 이 옵션은 시작할 때마다 레지스트리에 접속하므로, 네트워크가 없으면 이미 가진 이미지로 대체되지 않고 실행이 실패합니다. 이 모든 것은 실행 명령에 해당하는 내용입니다. Dev Container(2a~2c단계)는 사용자가 이미지를 받고, _Dev Containers: Open Folder in Container…_로 연결하고, _Dev Containers: Rebuild Container_를 선택할 때까지 만들어진 시점의 이미지를 유지합니다.

### 다음 단계 {#what-next}

`motir run`은 범위를 받습니다. 작업 항목 하나, 스토리 전체, 또는 활성 Sprint를 뜻하는 `sprint`입니다. `motir auto`는 대신 준비된 항목들을 사람 없이 비워 나가며, 한 번에 항목 하나씩 세션 브랜치에 반영합니다. 둘 다 받는 모든 플래그는 [{{value:cliPage}}](/docs/cli) 페이지에 있습니다.

## 무엇을 가두고, 무엇을 가두지 않는가 {#confines}

의존하기 전에 읽어 볼 만합니다. 이 세 가지 중 하나는 보장이 아니라 예외이기 때문입니다.

- **파일 시스템 — 격리됨.** 컨테이너 안에 있는 호스트 영역은 쓰기 가능한 `/workspace`와 읽기 전용으로 마운트된 에이전트의 자격 증명뿐입니다. Docker 소켓도, 다른 호스트 바인드도 없습니다.
- **네트워크 — 열려 있음, 의도된 설계.** 모든 에이전트에는 제공업체 API가 필요하고 디스패치된 모든 작업 항목에는 git 원격이 필요하므로, 이미지는 파일 시스템의 피해 범위를 제한할 뿐 외부로 나가는 트래픽은 제한하지 않습니다. 위협 모델에 더 많은 것이 필요하다면 Docker 자체의 네트워크 제어를 사용하세요. 컨테이너는 에이전트가 인터넷과 통신하는 것을 막지 않습니다.
- **권한 — 권한 없음.** `node` 사용자(uid 1000)로 실행되므로, 마운트에 쓰인 파일은 root가 아니라 사용자 소유로 남습니다.

## 환경이 제공하는 것 {#environment}

- **마운트된 사용자의 폴더.** `$PWD`가 `/workspace`가 되므로, 실행이 작업하는 체크아웃은 사용자의 것이고 실행이 만든 커밋은 종료 후 사용자의 디스크에 있습니다.
- **작업 항목마다 git 워크트리의 체크아웃 하나.** 실행은 사용자가 있는 트리를 편집하지 않고 항목마다 워크트리를 추가하므로, 병렬 실행이 브랜치 체크아웃에서 충돌하지 않습니다.
- **에이전트 자격 증명, 읽기 전용.** 프로필의 자격 증명 디렉터리는 `:ro`로 바인드 마운트됩니다. 컨테이너 안의 어떤 것도 이를 다시 쓸 수 없으며, 그에 관한 어떤 것도 Motir로 전송되지 않습니다. 직접 키를 가져오는 방식이므로 에이전트 비용은 사용자가 부담하고 API 호출은 우리를 거치지 않습니다.
- **미리 설치된 CLI.** 이미지에는 `motir`와 태그가 지정한 에이전트 바이너리가 들어 있으므로, 첫 실행 전에 설치할 것이 없습니다.
- **에이전트의 출력은 기본적으로 로컬에 남습니다.** 실행의 수명 주기 정보만 Motir에 전달됩니다. `--report-log`를 전달하면 출력의 끝부분도 추가로 전송되어 실패한 실행의 출력을 실행 페이지에서 볼 수 있습니다. 요청하지 않으면 꺼져 있으며, 어느 쪽이든 파일 내용, 경로, diff는 전송되지 않습니다.

## 토큰이 할 수 있는 일과 거부하는 일 {#token}

`motir login`으로 발급된 토큰은 고정되고 좁혀진 권한을 가집니다. 승인 화면이 이를 보여 주지만 바꿀 수는 없습니다. 더 넓게도 더 좁게도 못 하는데, 손으로 좁힌 권한은 사람 없이 도는 반복 작업을 도중에 깨뜨리기 때문입니다.

{{slot:grant}}

**토큰에 포함되지 않는 것은 `ai:view_plan`이며, 그 때문에 나오는 거부는 버그가 아니라 설계입니다.** 계획을 열려면 `work_item:edit`만 있으면 되므로 샌드박스 실행도 계획을 열 수 있고, 그러다 첫 번째 추가에서 거부됩니다. 제안을 추가할 때 검사하는 키가 바로 그것이기 때문입니다. 작업 항목을 수행하는 실행이 자신이 받은 계획을 고쳐 쓸 수는 없습니다. 이 거부를 만나면 에이전트가 올바르게 행동한 것입니다. 수정 사항을 댓글로 남기고, 항목을 차단된 상태로 두고, 멈춥니다. 잃어버리는 것은 없으며, 계획이 어떻게 되어야 하는지는 사람이 결정합니다.

더 조용한 실행을 원할 때 이를 더 좁히는 플래그가 둘 있습니다. `--disable-log-bug`는 에이전트가 다른 곳에서 발견한 결함에 대해 버그를 등록하지 못하게 하고(대신 댓글을 남깁니다), `--disable-replan`은 잘못되었다고 판단한 작업 항목에 대해 재계획을 제출하지 못하게 합니다(댓글을 남기고 멈춥니다). `motir auto`에서만 `--auto-approve-replan`이 반대로 작동합니다. 제출된 재계획을 승인하고, 사용자를 기다리며 멈추는 대신 반복을 계속합니다.

## 실행이 만드는 것과 확인하는 곳 {#produces}

- **브랜치와 풀 리퀘스트.** 항목이 반영되는 각 저장소에 만들어지며, 컨테이너 안에서 사용자의 git 자격 증명으로 푸시됩니다.
- **작업 항목의 링크.** 실행은 각 풀 리퀘스트가 어느 항목을 전달하는지 선언하므로, 병합하면 항목이 이동합니다. 항목 페이지의 개발 패널에 표시되는 것이 이 링크이고, 병합 시 항목을 닫는 것도 브랜치 이름이나 제목이 아니라 이 링크입니다.
- **진행 중인 상태.** 실행이 항목을 가져오면 진행 중으로 이동하고, 풀 리퀘스트가 열리면 구현됨으로 이동합니다. 검토 중은 검사가 통과하면 CI가, 완료는 병합이 기록합니다.
- **터미널.** `--report-log`를 전달하지 않으면 에이전트 자체의 출력은 사용자의 터미널에 남습니다.

## 작동하지 않을 때 {#troubleshooting}

### 에이전트 바이너리를 찾을 수 없습니다 {#agent-binary-not-found}

태그와 에이전트가 맞지 않습니다. 어떤 프로필을 시작했는지 확인하거나, `--agent <cmd>`로 실행이 다른 바이너리를 가리키게 하세요. `motir doctor`는 실행이 이 문제 때문에 항목을 헛되이 가져오기 전에 이를 알려 줍니다.

### 에이전트가 시작되었지만 인증되지 않았습니다 {#agent-not-authenticated}

자격 증명 마운트가 없거나 잘못된 디렉터리를 가리킵니다. 프로필마다 자신의 디렉터리를 마운트합니다. 실제로 받은 태그의 `{{value:dockerRun}}` 줄을 다시 실행하세요.

### 실행할 준비가 된 것이 없습니다 {#nothing-ready}

후보가 모두 충족되지 않은 의존성을 가지고 있습니다. `motir ready`가 후보 집합을 보여 주고, 작업 항목에 `motir show`를 실행하면 무엇이 막고 있는지 알려 줍니다. 그래도 디스패치하려면 `--force`를 쓰며, 항목 하나에만 적용됩니다.

### 제출된 재계획에서 실행이 멈췄습니다 {#stopped-on-replan}

에이전트가 작업 항목이 잘못되었다고 판단하고 수정된 형태를 제안했습니다. 의도된 멈춤입니다. Motir에서 계획을 읽고 승인하거나 거절하세요. 대신 사람 없이 도는 반복을 계속하려면 `motir auto`를 실행할 때 `--auto-approve-replan` 플래그를 함께 사용하세요.

### 실행이 종료된 후 작업이 남아 있습니다 {#work-left-behind}

워크트리와 브랜치는 마운트한 폴더 아래의 사용자 디스크에 있습니다. 중지된 컨테이너가 이를 가져가지 않았습니다. `motir done`은 병합된 항목을 정리하며, `--session <branch>`를 쓰면 병합된 세션 브랜치 전체를 정리합니다.

## 이 페이지가 다루지 않는 것 {#not-covered}

모든 명령과 플래그는 [{{value:cliPage}}](/docs/cli)에 있으며, 이 페이지는 CLI 자체의 카탈로그에서 생성되므로 어긋날 수 없습니다. CLI 없이 에이전트를 Motir에 직접 연결하는 방법은 [{{value:mcpPage}}](/docs/mcp)에 있습니다. 같은 작업 반복을 터미널이 아니라 HTTP로 구동하는 방법은 [{{value:apiPage}}](/docs/api)에 있습니다. 사용자 본인의 컴퓨터가 아닌 곳에서 샌드박스를 실행하는 방법은 아직 여기에 문서화되어 있지 않습니다. (VS Code 방식은 위에 문서화되어 있습니다. 이 문장이 예전에는 다르게 말했는데, 삭제된 섹션을 하나의 결정으로 기록하고 있었기 때문입니다.)
